I reviewed the diff adversarially. The new stale-detection/cache-closing logic has several correctness and operational hazards that happy-path tests (which call `closeStaleIndexDbs()` manually) won't reveal. Findings below, sorted by severity then confidence.

---

SEVERITY: CRITICAL
CONFIDENCE: medium
FILE: src/storage/sqlite/connection.ts:56
ID: connection.ts:56:sweep-closes-in-use-handles
ISSUE: `closeStaleIndexDbs()` closes connections purely from filesystem state, but callers hold the very handles it closes; this violates `closeIndexDb`'s own stated invariant that closing happens only "when this process is provably done reading through THIS handle."
ATTACK VECTOR: A caller does `const db = await openIndexDb(p); … await something; … db.prepare(...)`. Meanwhile another `openIndexDb` of a different path fires the 60s sweep, sees `p` stale (file replaced/deleted, or with finding #2 a stat blip), and calls `closeIndexDb(p)`. The caller's subsequent statement throws on a closed handle; if it had an open transaction, `db.close()` rolls it back → silent write loss. The tests never exercise a handle held across an await while the sweep runs, so this passes CI.
SUGGESTED FIX: Track per-path usage/refcounts (increment on open-return, decrement on release) and skip closing a path with active holders; defer stale-close until refcount hits 0.

---

SEVERITY: WARNING
CONFIDENCE: medium
FILE: src/storage/sqlite/connection.ts:38
ID: connection.ts:38:stat-error-masquerades-deleted
ISSUE: `fileIdentity`'s bare `catch { return undefined }` treats every stat failure (EMFILE, EACCES, EIO, EPERM) as "file deleted," so `isStale` returns true for a perfectly valid connection.
ATTACK VECTOR: This very change targets a process leaking 782 descriptors and 16 GB — i.e. a process already near fd exhaustion. Under that pressure `statSync` can fail with EMFILE for many paths at once; the next sweep then declares the entire cache stale and closes all of them, handing in-use callers closed handles (see #1) and inflicting a reopen storm. A momentary permission change on a directory does the same. The doc comment "whose file was deleted or replaced" is contradicted by this over-broad catch.
SUGGESTED FIX: In the catch, distinguish `ENOENT`/`ENOTDIR` (treat as stale) from all other errnos (treat as "unknown → do NOT close"); e.g. rethrow or return a sentinel that makes `isStale` return false.

ISSUE: Every `openIndexDb` for a cached path now performs a synchronous `statSync` (`isStale`), and the sweep does N synchronous stats + closes in one tick — blocking the event loop on the hot path.

**SEVERITY:** CRITICAL

**FILE:** src/storage/sqlite/connection.ts:111-120 (sweep inside openIndexDb) / closeIndexDb
**ID:** connection.ts:111:sweep-closes-live-handle
**ISSUE:** The stale sweep and per-open check call `closeIndexDb` on cached handles that were already handed out to previous callers, with no coordination with in-flight users of those handles.
**ATTACK VECTOR:** Caller A calls `openIndexDb(p)`, receives handle H, and starts an async write batch (the module's own docstring says writes are long-running and "an agent edits files faster than the previous write settles" — i.e., awaits are interleaved with work on H). During A's `await`, caller B triggers `openIndexDb`; the file was deleted/replaced, so B calls `closeIndexDb(p)`, closing H out from under A mid-transaction. A's checkpoint/commit fails on a closed handle, and the ROLLBACK helper can't help because the connection itself is gone. Same hazard for the 60s sweep, which can close any path in the cache, including ones actively being used by requests that finished their `await openIndexDb` moments ago.
**SUGGESTED FIX:** Track usage (refcount or "checked-out" set incremented when a handle is returned from `openIndexDb` and decremented when the caller releases it); skip closing in the sweep/per-open check while a connection is checked out, deferring to the next sweep.

**SEVERITY:** WARNING
**CONFIDENCE:** high
**FILE:** src/storage/sqlite/connection.ts:244-245
**ID:** connection.ts:244:identity-captured-after-open
**ISSUE:** The inode identity is captured *after* `openUncachedIndexDb` completes, so a file deleted/replaced between handle-open and `statSync` leaves a deleted-inode handle cached with a matching (new file's) identity — or with `undefined` identity, which `isStale` treats as "not stale" forever.
**ATTACK VECTOR:** Exactly the failure mode the comment promises is prevented: cleanup deletes the file in the window between SQLite opening it and `fileIdentity()` running. If a new file appears at the path, `statSync` returns the *new* inode and it's recorded as the identity of the *old* deleted handle — the stale handle is then trusted until the real file changes again. If no new file appears, `fileIdentity` → `undefined` and `identities.get` → `undefined`, so `isStale` returns false and the deleted handle is cached for the life of the process (the original 16 GB leak, reintroduced).
**SUGGESTED FIX:** Capture the identity *before/around* opening (stat, open, re-stat and confirm identity unchanged; retry if it changed), and treat "file missing but a connection is cached" as stale.

**FILE:** src/storage/sqlite/connection.ts:60-63
**ID:** connection.ts:60:inode-reuse-false-fresh
**ISSUE:** `dev:ino` identity can false-negative on inode reuse: a replacement file may land on the same inode, so `isStale` returns false and writes continue going through the old (possibly corrupt/leftover-WAL) handle.
**ATTACK VECTOR:** Cleanup deletes `t.index.db`; a new worktree creates a file at the same path that reuses the freed inode (common after mass deletions on ext4). `isStale` sees identical identity and returns the cached handle for the dead file. SEVERITY: WARNING

FILE: src/storage/sqlite/connection.ts:117
ID: connection.ts:117:close-stale-handle-unlinks-replacement-wal
ISSUE: When the file was replaced rather than deleted, `closeIndexDb` on the stale handle unlinks the `-wal` and `-shm` files that belong to the new database.
ATTACK VECTOR: The comment says the file "can go away … a reset replaces it". Suppose a reset or index-child process creates a new `x.index.db` and starts writing, so its WAL holds uncheckpointed commits. This process still holds the old inode, and SQLite on that inode sees itself as the last connection. `db.close()` therefore checkpoints and then deletes `x.index.db-wal` and `x.index.db-shm` BY NAME. Those are now the new database's files. The other process keeps its open descriptors, but any later connection sees no WAL, so committed-but-uncheckpointed transactions are lost or the index is inconsistent. The sweep makes this more likely, because it closes handles on a timer rather than only when this process next opens that path.
SUGGESTED FIX: Treat "path missing (ENOENT)" and "path now has a different inode" separately. For a replaced file, drop the handle without letting SQLite delete the WAL by name. For example, skip the checkpoint and accept that the descriptor leaks, or rename or hard-link the new `-wal` and `-shm` out of the way first. Add a test for the replaced-inode case, because the current tests cover only deletion.

SEVERITY: WARNING
CONFIDENCE: medium
FILE: src/storage/sqlite/connection.ts:301
ID: connection.ts:301:stale-close-checkpoints-into-deleted-file
ISSUE: Closing a stale handle still runs the unconditional `wal_checkpoint(TRUNCATE)`, which copies the whole WAL into a file nobody will read and fsyncs it.
ATTACK VECTOR: The incident that motivated this change involved hundreds of deleted index files and WALs measured in GB. `closeStaleIndexDbs` runs synchronously inside `openIndexDb`, on the daemon's single event-loop thread. SUGGESTED FIX: Give `closeIndexDb` a `{ stale: true }` path that skips the checkpoint and calls `db.close()` only. Alternatively, have the sweep close at most N handles per call.
