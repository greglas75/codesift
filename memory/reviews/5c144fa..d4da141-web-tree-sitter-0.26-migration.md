by symbol-count comparison rather than by the suite alone. One finding from the

pre-existing debt in code the reviewers saw as diff context, or refuted below.

## What changed and why

web-tree-sitter 0.26 removed the default-export namespace. 539 type errors, of
which **449 were a single pattern** — `Parser.SyntaxNode` / `Parser.Tree` /
`Parser.Query` became top-level `Node` / `Tree` / `Query`. Only six namespace
members were ever used, so one scripted pass over 56 files cleared them, and the
114 "implicit any" errors were pure cascade.

The substantive remainder:

- `Parser` is a named class, not a default export; `Parser.Language.load` is now
  `Language.load` (`src/parser/parser-manager.ts:1`).
- `parser.getLanguage()` is the `parser.language` property
  (`src/tools/ast-query-tools.ts:53`).
- Queries are built with `new Query(language, source)`
  (`src/tools/ast-query-tools.ts:60`).
- **`parse()` returns `Tree | null`.** 29 call sites assumed success. Each guard
  mirrors what that site already did on a parse THROW, so behaviour is unchanged
  where a tree exists and a failed parse now takes the path the code had already
  chosen for the failure it did handle. In `src/utils/import-graph.ts:549` the
  guard additionally prevents caching a null tree as though it had parsed.

## MUST-FIX — applied

**R-1 `parseFile` cast away the nullable parse result.**
`src/parser/parser-manager.ts:210` declared `let tree: TSTree` and cast the
`Promise.race` result `as TSTree`. Raised as CRITICAL by the adversarial pass;
investigation showed it was **half right** — the `if (!tree) return null` guard
below already handled it at runtime, so this was a lying type rather than a
hole. Declaration is now `TSTree | null` and the cast is gone, which makes the
existing guard type-meaningful. Confidence 100/100.

## Refuted — investigated, evidence says no

- **`review_diff` reports 12 removed exports** (`GET`, `metadata`, `onRequest`,
  `generateStaticParams`, …). `git diff` over those files shows **no line
  containing `export` was changed at all**. The check compares INDEXED symbols
  across refs, and the two indexes were built by different parser versions — so
  it is measuring an extraction delta, not an API change. This check is
  unreliable across any parser bump.
- **"Named import of `Parser` will cause a compilation error"**
  (`src/tools/astro-middleware.ts:14`, CRITICAL) — typecheck is clean; `Parser`
  is a named export in 0.26.
- **"`Parser` is exposed as the default export"** (`src/tools/taint-tools.ts:4`)
  — that was true in 0.24 and is precisely what this migration changes.
- **Next.js readers "still assume non-null Tree"** — they parse through
  `src/utils/nextjs-audit-cache.ts`, not `parser.parse()` directly; typecheck
  would have caught an unguarded deref.

## Backlogged — real, pre-existing, out of this diff's scope

The adversarial pass surfaced substantial pre-existing debt in the extractor
layer it saw as context. Not introduced here, not fixed here:

- **WASM lifetime**: parsed `Tree` and `Query` objects are never `.delete()`d in
  `ast-query-tools`, `astro-config`, `python-circular-imports`,
  `nextjs-audit-cache`; `parse-cache.ts:68` discards a tree without deleting it.
  web-tree-sitter ≥ 0.25 makes explicit disposal more consequential.
- **`parser-manager.ts:205` timeout race can never win** — `parser.parse()` is
  synchronous WASM, so the event loop is blocked for the whole parse and the
  `setTimeout` cannot fire until it finishes.
- Guards added here are silent: no log, no skipped-file counter, so a repo whose
  files stop parsing looks identical to a repo with no symbols.
- Extractor-level correctness reports (PHP `use_declaration` trait detection,
  chained Hono route receivers, CJS `module.exports =` matching, namespace-
  qualified heritage names, `ts-imports` named-children traversal).
