## Why this review found what adversarial did not

Three adversarial rounds plus two more during the ship all worked on **the diff**. Two whole
classes of defect are invisible from there:

1. **The gate list sees what the diff omits.** The CQ auditor asked "is this secret protected at
   rest" — a question about a file the diff never touches. Result: R-1, the bearer token written
   world-readable to three config files. Five passes on token-on-the-wire never asked it.
2. **The call graph sees what the diff cannot reach.** The behaviour auditor traced the changed
   `getCodeIndex` contract *outward* to its consumers. Result: R-3, two pre-existing call sites
   that swallow the new error and reinstate the exact bug this release removes.

## Findings — MUST-FIX, all applied

**R-1 [CQ-2, conf 65] Bearer token written to disk without restrictive permissions**
`src/cli/setup/fs.ts:42`, `src/cli/setup/codex.ts:96`, `src/cli/service.ts:306`
All three token-carrying writes used the default umask (commonly 0644). The shared-daemon feature
exists so one HOST serves several machines, so "another local account can read this file" is the
designed-for scenario, and the file grants every tool on the daemon — i.e. read access to every
indexed repository. Now 0600 at creation **plus an explicit chmod**, because `mode` applies only
when a file is created and a config written by an earlier version would have stayed 0644 forever.
Tested, including that rewrite case.

**R-2 [CQ-1, conf 55] Non-constant-time bearer comparison**
`src/server.ts:175` — `auth !== \`Bearer ${token}\`` short-circuits at the first differing byte,
leaking prefix-match length through response time. Now `timingSafeEqual`, length compared first
because it throws on mismatch.

**R-3 [BEHAV-1, conf 88] The new storage-fault contract was swallowed by two callers**
`src/tools/workspace-tools.ts:443`, `src/tools/workspace-scope-helper.ts:31`
`getCodeIndex` was changed this release to THROW `IndexStorageError` instead of returning null,
so tools stop rendering a storage fault as an authoritative empty answer. Both of these
blanket-catch and coerce to null. They feed `list_workspaces`, `workspace_graph`,
`affected_workspaces`, `workspace_boundaries`, and the `workspace=` parameter on
`framework_audit`, `nextjs_route_map`, `nextjs_metadata_audit`, `analyze_hono_app`, `nest_audit`,
`astro_audit`. On a monorepo with an unreadable index every one of them reported "no workspaces"
with full confidence — the failure this release exists to remove, reappearing one layer out
because the contract changed without auditing its consumers. Both now rethrow.

**R-4 [ADV, conf high] Three divergent definitions of "loopback"**
`src/utils/loopback.ts` (new) — `server.ts` gated the bind on a 3-string set, `cli/service.ts`
had its own copy of the same three, `cli/setup/mcp.ts` had the full one. **Verified before
fixing, and the reported direction was wrong**: server and service AGREE and are both too narrow.
Binding to `127.0.0.2` — an ordinary loopback alias — was accepted by setup and refused by the
daemon. All three now import one module. This WIDENS the no-token bind set, so there is an
explicit test that everything routable is still refused, plus one asserting the three layers agree.

## Refuted, with evidence

**"`appendSharedCache` is called without await/catch — unhandled rejection can crash the daemon"**
(adversarial CRITICAL, high confidence, raised twice). `src/storage/shared-embedding-cache.ts:98`
is `export function ... : void` — synchronous (`appendFileSync`), and its body is wrapped in a
try/catch that deliberately swallows so a cache write cannot fail an indexing run. No promise
exists to reject. The providers inferred "async" from the name and the presence of I/O.

**"Migration is permanently skipped by a partial or empty DB, orphaning the legacy JSON"**
(adversarial CRITICAL, medium). `loadIndexSqlite` returns non-null only after the `repo`/`root`
meta write, which is the last statement inside one `BEGIN`/`COMMIT` — a crash mid-write rolls
back and reads as empty. Both real `saveIndex` callers were traced: `folder-indexer.ts:202` reads
(triggering migration) before writing at :413; `conversation-index-tools.ts:134` rebuilds its
full symbol set from source on every call, so there is no legacy data to lose. Noted as accidental
call-site discipline rather than an enforced invariant — recorded, not fixed.

**"`loadIndexSqlite` leaks a connection per read"** (2 providers, high confidence, earlier round).
`openIndexDb` caches connections by path and reuses them; closing per read would destroy the
cache this migration depends on.
