## Findings — all applied

**R-1 [MUST-FIX] The staleness check was a lookalike, not parity.**
`src/tools/index-tools/registry.ts:216` — `getIndexSummary` used `isExtractorVersionCurrent`, which
short-circuits `if (!index.extractor_version) return false`. `getCodeIndex` goes through
`loadIndexOrStale` → `collectExtractorVersionMismatches`, which only flags a language it can see
among `files`. An index with no `extractor_version` whose files are entirely in languages absent
from `EXTRACTOR_VERSIONS` (go, rust, markdown, sql, prisma) therefore loaded fine through
`getCodeIndex` and returned null here. `index_status`'s fallback probe re-runs `loadIndexOrStale`,
which also reports ok, so it matched neither the stale nor the unreadable branch and fell through to
a bare `{indexed:false}` **with no diagnostic field** — a correctly-indexed repo reported as never
indexed, confidently and silently. Both paths now call one function. Found by BEHAV-1.
*This directly contradicted the commit message, which claimed parity.*

**R-2 [RECOMMENDED] `summariseIndex` aliased the cache's arrays.**
`src/storage/index-store.ts:304` — `files` and `workspaces` were passed by reference while the main
caller projects an index living in `codeIndexes`, so one caller's `sort`/`splice` would rewrite what
every later reader is handed. This is the boundary `copyIndex` exists to defend, reached by another
route. Now copied. Found by adversarial (2 providers) and BEHAV-2 independently.

**R-3 [RECOMMENDED] The new SQLite read path shipped untested.**
`loadIndexSummarySqlite` had zero test references: the status tests mock `getIndexSummary` wholesale,
so the transaction, the SQL `COUNT(*)`, the empty-index early return and the file ordering were all
uncovered. Six tests added in `tests/storage/index-summary.test.ts`, including that `symbol_count` is
recomputed rather than echoed from a stored field that disagrees.

**R-5 [MUST-FIX] The narrowed path threw away the fault detail.**
`src/tools/index-tools/registry.ts:236` — `getCodeIndex` embeds the underlying error text in the
`IndexStorageError` message; `getIndexSummary` carried only the classified code, keeping the detail
in `.cause`. But `index_status` copies `err.message` verbatim into `unreadable.message`, the one
field whose entire job is telling an agent WHAT went wrong — so the new path said "something is
broken" where the old one said which thing. Strictly worse diagnostics from a change whose point was
to lose nothing. Found by the CQ auditor; no other lens saw it.

**R-6 [RECOMMENDED] Stale-branch logging went dark.**
`getCodeIndex` warns with language/expected/actual; the summary path returned null silently, so the
server log said nothing for a stale repo whose only traffic is `index_status`. Now mirrored.

**R-7 [RECOMMENDED] The storage-fault branch had never been executed under test.**
Pre-existing (identical gap at `f8979e5`) but load-bearing once R-5 changed that path's message. Two
tests added: the fault is reported with its detail intact, and a non-storage error propagates rather
than being rendered as an empty index.

**R-4 [NIT] File ordering could differ between the two SQLite read paths.**
`SELECT * FROM files` had no `ORDER BY` while `readTablePaged` walks by rowid. Now `ORDER BY rowid`,
so a caller comparing a summary against a full load cannot see a difference that is not in the data.

## Rejected, with reasons

- **"The cache-hit shortcut skips the staleness check."** Raised by two independent providers.
  `codeIndexes` is written in exactly one place (`registry.ts:175`), only after `loadIndexOrStale`
  reports `ok`, and `EXTRACTOR_VERSIONS` is a module constant that cannot drift inside a process — a
  cached entry is version-validated by construction, and `getCodeIndex` takes the same shortcut. Not
  a divergence. The code now states this, since two readers did not see it.
- **"`NaN` from corrupt meta values."** `Number(meta(...) ?? 0)` matches `loadIndexSqlite` exactly;
  changing it here alone would create the inconsistency it claims to fix.
- **"The swap stops rejecting indexes with no `extractor_version`."** Raised on the fix diff. That
  is the intended outcome, not a regression: `getCodeIndex` has always tolerated exactly this case
  via the same function. Restoring the rejection would recreate R-1 in the opposite direction.
- **"Shallow copy leaves `FileEntry` objects aliased."** Matches `copyIndex`'s documented decision —
  the array container is the boundary that was being crossed; elements are treated as immutable
  records. Deviating here alone would make the two copies inconsistent.
- **"`lossy_migration` truthiness differs between backends."** The SQLite path reads a meta KEY
  (presence is the storage contract) and the JSON path reads a boolean FIELD. Different sources,
  both correct.

## Quality wins

- `IndexSummary` omits `symbols` rather than defaulting it to `[]`: a type-level guard against the
  empty-reads-as-authoritative failure mode, verified by a test asserting the field is absent.
- The one-transaction discipline for `files` + meta is carried over from `loadIndexSqlite`, with the
  comment explaining why splitting the reads is a narrower window rather than a closed one.

## Backlog

- **B-7** `EXTRACTOR_VERSIONS` (`src/tools/index-shared.ts`) has no entries for go, rust, markdown,
  sql, prisma, swift, dart despite extractors existing for several. Pre-existing; it is what made
  R-1's trigger reachable.
- **B-8** `loadIndexSummarySqlite` reads the whole `files` table in one `.all()` with no
  `setImmediate` yield, unlike `readTablePaged`. Harmless while `files` stays orders of magnitude
  smaller than `symbols`; revisit if that changes.
- **B-9** `summariseIndex`'s `[...index.files]` would throw on a malformed index with no `files`,
  and the cache-hit call site sits outside `getIndexSummary`'s try. Unreachable through the typed
  path (`files` is required on `CodeIndex`) but not defended.
- B-2..B-6 from the previous review remain open.
