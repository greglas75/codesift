## What changed

Every index read failure used to collapse into `null`, and `null` means "this repo has no
index". A locked, corrupt, or permission-denied store therefore reached tools as an unindexed
repo, which they render as an authoritative empty answer — and the remedy it implies
(`index_folder`) is wrong against a database that is merely busy.

- `IndexStorageError` (`code`, `path`) for operational failures; `classifyStorageError` is a
  tight allowlist so ordinary absence is never converted into a throw.
  (`src/storage/sqlite-index-store.ts:60`)
- `loadIndexOrStale` gains `{status:"unreadable", reason, code, message}`.
  (`src/storage/index-store.ts:96`)
- `getCodeIndex` throws instead of returning null — null is the channel tools turn into
  "no results". (`src/tools/index-tools/registry.ts:135`)
- `index_status` is the deliberate exception: it reports `unreadable: {code, message}`.
  (`src/tools/status-tools.ts:64`)

All three are the original bug in narrower gaps: **defaulting to "absent" when we do not know.**

## Refuted, with evidence

**"`loadIndexSqlite` never closes its connections — a descriptor leak per read"** (2 providers,
both high confidence). `openIndexDb` caches connections by path and reuses them
(`src/storage/sqlite-index-store.ts:196`); there is no per-call open, and closing in a `finally`
would destroy the cache the migration's read performance depends on. The providers could not see
that code because it sits outside the diff. The same mechanism produced the *true* finding R-1:
a handle from a FAILED init is the one case that never reaches the cache.
